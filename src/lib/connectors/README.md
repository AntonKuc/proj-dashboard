# Коннекторы внешних сервисов

Каждый файл в этой папке — точка подключения одного внешнего сервиса.
Сейчас это заглушки: они бросают понятную ошибку, если нужные ключи
не заданы в переменных окружения. Как только дашь доступы — допишем
реальный вызов API внутри `fetch...()` и данные, которые он вернёт,
будем писать в таблицу `Metric` с соответствующим `source`.

## Такском Касса (`taxcom.ts`)
Нужно: базовый URL API, логин/токен доступа к личному кабинету Такском Касса.
Даёт: выручку по чекам, разбивку по точкам продаж — обычно закрывает
статьи "Выручка", "Выручка ОФД".

## 1С (`onec.ts`)
Нужно: адрес 1С:Предприятие с включённым HTTP-сервисом (или обмен через
1C:Fresh/облако), логин/пароль или сервисный аккаунт.
Даёт: себестоимость, ФОТ, обязательные платежи, налоги — управленческие
проводки, которые сейчас руками сведены в файле.

## Google Диск (`gdrive.ts`)
Нужно: OAuth-клиент (Client ID/Secret) или service account с доступом
к нужным папкам/таблицам на Google Диске.
Даёт: исходные файлы отчётности (например, обновлённый xlsx), которые
можно парсить автоматически вместо ручной загрузки.

## Яндекс Карты (`yandexMaps.ts`)
Нужно: API-ключ Яндекс Карт / Яндекс Бизнес.
Даёт: данные по точкам (рейтинг, отзывы, координаты) — для карточки
проекта, не для P&L.

У Яндекс Карт (как и у 2ГИС, Google) обычно нет публичного API для
чтения отзывов — если ключ Яндекс Бизнес не даёт нужных данных,
единственный рабочий вариант — забирать через браузерную сессию.
Рабочая схема (проверена на практике на похожих проектах):

- Отдельный VPS (2vCPU/4GB достаточно) — Playwright/Selenium + cron,
  при необходимости VPN до сервиса.
- **Логин руками, локально, не с сервера.** Headless-браузер на VPS
  почти всегда палится антибот-системами (нет GPU → WebGL через
  software-эмуляцию, TLS-фингерпринт датацентра — обе вещи легко
  детектируются). Схема: логинишься руками в обычном браузере →
  экспортируешь сессию (cookies/localStorage, например
  `context.storage_state()` в Playwright) → заливаешь файл на сервер —
  дальше сервер использует готовую сессию, не логинится сам.
- Сессия протухает непредсказуемо (от часов до нескольких суток).
  Три меры вместе: (1) keepalive-крон на сервере раз в час — заходит
  с текущей сессией, если жива — пересохраняет; (2) по возможности
  автообновление сессии с рабочего компьютера (куки из обычного
  браузера через расписание); (3) уведомление о статусе сессии, а не
  узнавать о протухании только по факту упавшего ночного сбора.
- **Retry с бэкоффом на HTTP 429 — на каждом запросе**, не только на
  "главном" месте вызова. Похожий соседний метод запроса легко
  словит тот же rate-limit, если про него забыли.

## Общий принцип для всех коннекторов: стабильный ключ сущности

Для связи с записью в нашей БД используй **внутренний ID сущности из
источника** (id блюда/точки/заказа в кассе или агрегаторе), а не
производные вещи вроде названия или URL. Название блюда могут
переименовать в кассе, промо может временно менять отображаемое имя —
если ключом связи была строка, а не ID, история/аналитика по этой
сущности после переименования молча "обнулится" (система решит, что
это новая сущность). Закладывай ID-ключ с первого дня интеграции, а не
когда уже накопится история.

Каждый коннектор экспортирует одну async-функцию с чётким контрактом
входа/выхода — смотри комментарии в файле.
